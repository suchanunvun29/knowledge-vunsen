## Issues Found — Phase 2

1. ~~**`ImportBatch` totals/`sheetsFound` not persisted when the import transaction fails**~~ — **Resolved and re-confirmed live** (2026-08-15, targeted round). `backend-engineer`'s fix in `import.service.ts`'s `catch` block now persists `totalRows`/`insertedRows`/`updatedRows`/`errorRows`/`skippedRows`/`sheetsFound`/`periodsTouched` on every failure path, using the values already computed during parsing (before the transaction starts). Reproduced live via a real two-concurrent-`POST /import` collision — see Per-Task Results above for the exact numbers observed.
2. **`skippedRows` is never populated by anything, in any code path** (design/schema ambiguity → **`system-analyst`**, unless the user just wants to decide the definition directly). `design.md`'s `ImportBatch` model has `skippedRows` as a field distinct from `errorRows`, but the "Import Rules" table only ever says ERROR-level rows get "ข้ามแถว" (skipped) — which the implementation counts under `errorRows`, not `skippedRows`. Genuinely blank rows (all mapped columns empty) are silently `continue`d in the parsing loop without incrementing either counter. The result: `skippedRows` renders as `0` in the frontend's stat cards on every single import, successful or not, which isn't wrong per the letter of `design.md` (nothing defines what should increment it) but doesn't match what a manager would reasonably expect a field literally named "skipped rows" to show. Not blocking — this is cosmetic/informational, not a data-correctness issue — but the contract needs a clear definition (e.g., "blank rows silently excluded" vs. removing the field's separate meaning entirely) so it either gets wired up or is explicitly documented as always-zero. **Still open** — carried to main `review.md` Open Issues.
3. **Concurrent-import fail-fast behavior** — re-confirmed as intentional and reasonable, not a defect, consistent with the already-accepted note. Live-tested: two real concurrent `POST /import` calls resulted in one committing normally (~2 min for 846 rows against the remote Supabase pooler) and the other failing in ~1.3s with a clear Thai error message, no hang, no corruption. For a ~15-user internal tool doing occasional monthly imports, this is a sound tradeoff versus queueing, which would add real complexity (a job queue/worker) for a collision that's rare in practice. No action needed unless the user specifically wants queueing instead.
4. **Security review still outstanding for this module**, same flag as Phase 1's own note. `design.md` explicitly marks Module C `⚠️ Sensitive` ("รับไฟล์จากภายนอก...zip bomb, สูตรใน cell, การใช้หน่วยความจำ"). Not a defect found by this functional pass, but `security` should specifically look at: the 20MB upload limit combined with in-memory `exceljs` parsing (memory exhaustion potential from a maliciously crafted small-but-dense `.xlsx`), the unresolved-`sharedFormula`-cell handling (confirmed to fail safely into `INVALID_NUMBER` rather than crashing, but worth a deliberate look), and whether `.xlsx`-extension + MIME-type filtering alone is sufficient given `exceljs` parses the file content directly afterward. **Still open** — carried to main `review.md` Open Issues.
